# Status

Updated 2026-10-25.

## What works

- Multiplayer control response: held flight/EVA inputs at 20 Hz with immediate key changes; bounded quaternion attitude prediction and correction for the flight model and navball, reset on discontinuities. Native regression tests and a browser launch/steering test with 30 ms added round-trip delay cover the changes; see [multiplayer performance](multiplayer-performance.md).

- Multiplayer streaming builds and encodes periodic world snapshots and trajectories once for all players. Connections share encoded buffers, skip superseded pending updates, and disconnect after a five-second stalled write. Nine-connection consistency coverage and an optional 1/4/16-player latency probe are described in [multiplayer performance](multiplayer-performance.md).

- Part rigs and animation (protocol v28): generic TRS clip import, retained bone hierarchies, four-weight skinning, interpolation/looping/seeking, masked pose blending and late aim/position constraint APIs. Solar-panel and retractable-gear flight state now drives the original part clips per instance, including reversal, pause/warp and late-join terminal poses. Deployment snapshots identify individual solar panels; generic deployables are no longer mistaken for solar producers. Original-asset deformation and a three-model Chromium/WebGPU instance-isolation test pass. Character retargeting/state machines and procedural gimbal/tracking/wheel animation remain incomplete. See [rig and animation comparison](reference-notes/rigs-and-animation.md) for evidence, reproduction and remaining gaps.

- Flight engine effects (protocol v25): original engine plume meshes/morphs, exhaust shader arithmetic, full-resolution compressed textures/mips, and authored ignition/shutdown/smoke recipes. Heat refraction and HDR bloom are integrated with the scene. Static pressure and fuel-fed engine indices come from the server. `tools/export_particles.py` exports 35 engines, 53 nozzles and two contextual prefabs into `assets/web/fx/`. A 36-frame comparison against original Direct3D shader bytecode passed with worst effect-relative RMSE below 0.005%; this verifies plume shaders, not full Unity particle lighting or whole-game parity. See `docs/reference-notes/particles.md` for reproduction and remaining limits.

- Cargo workspace with seven crates (`ose-math`, `ose-data`, `ose-sim`, `ose-net`, `ose-server`, `ose-client`, `ose-importer`). `cargo test --workspace`, `cargo clippy -D warnings` and the wasm check all pass. `trunk build` in `crates/ose-client` produces a loadable page (no game logic in the client, see ADR-0002).
- `ose-math::Orbit`: Keplerian elements <-> state vectors, the original's anomaly solvers and tolerances, propagation, time to true anomaly, true anomaly at radius; 7 tests including elliptic/hyperbolic round trips.
- `ose-sim::bodies`: bodies as ECS entities with `OnRails` orbits, star-space position by walking the parent chain, `main_body_at` (SOI containment). `cargo run -p ose-sim --example kerbol` loads the converted data and prints every body; Kerbin comes out at 13,599,840 km and 9284.5 m/s, Mun at 12,000 km, Minmus at 47,000 km.
- `ose-sim::trajectory`: patched-conic predictor (`predict`): collision, encounter (sampled closest approach refined with the original's halving-step and SOI bisection solvers, 0.01 s tolerance), escape and final patches with handoff via state vectors. Parity: a 100 km Hohmann transfer to the Mun enters its SOI 19,941 s after the burn (the bot's independent estimate: 19,950 s) and, with no lead error, impacts the Mun as the bot predicted.
- `ose-sim::vessels`: vessels on rails as entities; `update_reference_body` re-expresses the orbit around whichever body's SOI contains the vessel (escape and encounter), with tests showing the handoff keeps the star-space position continuous.
- `ose-server` streams the universe: `/ws` session (`Hello` -> `Welcome` + `BodyCatalog`, then `TimeState` + `Snapshot` at 10 Hz with star-space position and velocity of every body, `RequestWarp` sets the warp). The Kerbol system (17 bodies, `assets/own/kerbol-system.json`) is embedded in the binary; `--bodies PATH` overrides. `crates/ose-server/tests/ws_session.rs` spawns the binary and checks the whole session. Protocol version 2 in `ose-net`.
- `ose-sim::Universe` drives vessels: each step advances up to `warp` ticks but never past a vessel's next predicted SOI transition (the original's timescale override), then runs the SOI handoff for every vessel. `spawn_vessel`, `spawn_vessel_in_circular_orbit`, `vessel`, `predict`.
- Powered flight v1 (`ose_sim::flight`, protocol v45): a vessel on the pad or in the air is a point mass integrated every tick in its body's inertial frame with thrust from the current stage (vacuum/sea-level Isp from the craft's staging report), propellant consumption, gravity, atmospheric drag on one reference area (density from the body's pressure and temperature curves), surface contact with crash detection above 12 m/s, co-rotation while landed, staging and attitude holds (up, surface/orbit prograde and retrograde, normal, radial, pitch+heading, fixed vector). `LaunchOnPad` / `LaunchSavedOnPad` put a craft on the KSC pad, `SetControls` and `Stage` fly it, and `VesselState.flight` streams situation, altitude, speeds, throttle, stage, propellant, mass, thrust, TWR and dynamic pressure. Warp is capped at 4 while any vessel is under powered flight; after 10 s of unpowered coasting above the atmosphere the vessel hands off to rails and keeps its flight state (stage, propellant, mass) as `Dormant`. `SetControls` with throttle above zero wakes a dormant vessel at its rails position, so burns from orbit, captures and descents are flown under power; `Stage` works on rails too. Crafts launched straight into orbit (`LaunchCraft`) carry a dormant flight state; the bare per-player probe has none and is refused. A powered vessel crossing a sphere of influence is re-expressed around the new body without a jump. Dormant state is saved and restored. Tests: a two-stage test rocket flies a scripted gravity turn from the pad to a 70 km+ orbit; a stock Kerbal K1 lifts off in the session test; hard landings crash and soft ones do not.
- Part structure (`ose_sim::rigid`, `ose_sim::structure`): every craft launched on the pad or into orbit carries its parts as rapier rigid bodies joined by fixed multibody joints, with the original's joint break limits (`breakingForce` / `breakingTorque` x node factor x 50, size-2+ nodes divided by 3). Each flight step loads the structure with the delivered thrust on the burning stage's engines and the drag on each part; joint force and torque come from Newton-Euler over the subtree each joint carries. A joint over its limit breaks, the pieces away from the root become debris vessels with their mass and propellant (owned by the pilot, `"<name> debris"`), and lost engines scale the stage's thrust. Staging trims the structure to the next stage's parts. Wobble: every non-rigid joint bends with the original's angular spring (`JOINT_RIGIDITY x nodeFactor x 10`, damping 1%) and the moment of inertia of the subtree it carries, driven by the torque the rigid solution puts through it and integrated semi-implicitly in substeps, so boosters on radial decouplers and tall stacks flex under thrust, ring after a sudden load and settle; turning the vessel loads it too (wheel torque at the root, gimbal side force at the engines, tangential and centripetal loads on every part). Joints break on their spring torque, so a ringing joint can fail where a steady one would not. `FlightReadout` (protocol v11) adds `joint_stress` (worst joint load against its limit) and `flex` (each bent part's rotation and offset in the craft frame). Tests: the Kerbal K1 and a small rocket hold under full thrust; the K1 flown broadside at 900 m/s, 3 km up, sheds parts; an overloaded joint splits a craft.
- Drag cubes (`ose_sim::aero`): with a structure, drag is the original's six-face drag cube model per part (tip, surface and tail curves against Mach, the drag-coefficient and Cd-power curves, pseudo-Reynolds, faces covered by stack neighbours removed), turned to `Cd * A` and fed to the point-mass integrator; the reference-area drag remains for vessels without a structure (debris, old saves). The slim catalog keeps each part's stowed cube (packed or retracted shape first). A bare 1.25 m tank nose-on at 100 m/s at sea level draws a few kN; the K1 has about 2.4 m^2 `Cd * A` nose-on and 13 m^2 broadside at Mach 0.3.
- Resource flow graph (`ose_sim::resources`): the original's part flow graph (an edge each way per attachment, crossfeed from the part the edge leaves, decouplers as structure boundaries) with its flow modes: `NoFlow` (solid fuel stays in its booster), `AllVessel`, `StagePriorityFlow` (groups by decoupler distance, nearest first; electric charge, monopropellant, xenon) and `StackPrioritySearch` (tanks reachable over crossfeed; methane, oxidizer). Requests drain group by group, proportionally to each tank's contents inside a group, with one delivered fraction shared by a request's ingredients. A vessel with a structure burns its propellant through the graph per engine (split by rated thrust); its mass, reachable propellant and thrust (engines attached and fed) come from the tanks every step, and staging and breakups drop the actual tank contents. Fuel lines are not modelled yet. Tests: stacked tanks drain at the same fill ratio, the decoupler isolates the upper stage, a starved engine gets the fraction left for both ingredients, the K1 burns boosters and core together and stages the boosters off with their leftover solid fuel.
- Electric charge (`Structure::electric`, rates from the part data: `Data_Command.requiredResources`, `Data_ReactionWheel.RequiredResources` per kN*m, `Data_SolarPanel.ResourceSettings`, `Data_ModuleGenerator.ResourceSetting`, kept in `PartDef.electric` by the importer): solar panels charge by starlight (inverse square against the home world's distance, zero in the shadow of the vessel's body or the planet it orbits; fixed panels at half rating since roll is not simulated), engine alternators while their engine runs and RTGs always; probe cores and reaction wheels (in proportion to how fast the vessel is turning) draw through the flow graph. Wheels without charge give no torque; an uncrewed vessel whose cores have no charge loses control (no steering, throttle cut, `SetControls` refused). Deployable panels count as deployed and transmitters draw nothing yet. `FlightReadout` (protocol v10) adds `electric_charge`, `electric_capacity` and `has_control`.
- Science and the tech tree (protocol v13, run times v14; `docs/reference-notes/science.md`): the original's 8 experiments, every body's science regions with their baked maps (512 x 256 in `assets/own/science/regions.bin`) and landmark sites, and 87 tech nodes. A vessel's situation (landed, splashed, atmosphere, low or high orbit) and region come from its position; `RunExperiments` runs its parts' experiments where valid (crew and charge permitting; experiments with a `TimeToComplete` run that long, draw their charge per second, wait without it, are interrupted by leaving their situation or region, and end in `ExperimentFinished` to the owner) and the reports ride along until `TransmitScience` or `RecoverVessel` (landed on Kerbin, removes the vessel). Values are the original's (`DataValue x body x situation x region` scalars), each report key scores once per campaign, points are submitted reports rounded times `ScienceRewards` plus mission rewards times `MissionRewards`, and `UnlockTechNode` spends them on nodes whose prerequisites are unlocked. In Exploration campaigns the pad refuses crafts with parts the agency has not researched (campaign members only; `LaunchCraft` to orbit stays a dev shortcut). `ScienceState` (capacity, allocated, unlocked nodes, submitted reports, missions) answers `ScienceInfo` and is pushed to everyone when it changes; `/tech-tree.json` and `/missions.json` serve the definitions.
- EVA and crew (protocol v15, `ose_sim::crew`): crewed parts are seated at launch (Jebediah, Bill, Bob, Valentina, then the roster). `GoEva` puts a Kerbal outside as a vessel of their own (beside the craft on the ground, 2.5 m off it in flight) with the original's jetpack (0.25 kN, 0.025 t of propellant; Isp 100 s is our choice), flown with `SetControls`; `Board` climbs back into a craft within 6 m with a free seat; `PlantFlag` plants a flag vessel beside a Kerbal standing on the ground (missions' flag events). EVA Kerbals carry the `eva_kerbal` part's experiments (surface sample, crew observation, 10 s each). `FlightReadout` adds `crew`, `eva`, free `docking_ports` and `docked` joints.
- Docking (`ose_sim::docking`): every vessel keeps its craft. Two vessels' free docking ports of a matching size latch when within the acquire range, facing each other within the acquire angle and drifting slower than 1 m/s (the original pulls them together with its acquire force and latches at the capture range; we latch at once); the second craft is turned port-to-port, re-rooted at its port and attached under the first, tanks, crew, reports and staging carried over, and `Docked` goes to both owners. `Undock` splits at the joint into a new vessel pushed off by the port's ejection force for a second; the two cannot relatch until 3 m apart. Saves keep each vessel's current craft (lost parts out, tanks as they were), crew, docked joints, EVA Kerbals and flags, so restored vessels get their part structure back.
- CommNet (protocol v16, `ose_sim::commnet`): as the original's `GetConnectedNodesJob`: the KSC is the source (8e11 m), each vessel a node with its best antenna's range (`Data_Transmitter.CommunicationRange`), two nodes link when each is within the other's range (bodies do not block), and every vessel relays. Transmitting needs a link; with `CommNetRequired` a probe core that needs CommNet cannot be flown out of contact. `FlightReadout` adds `comm_connected`, `comm_hops`, `comm_range_m`.
- Ground contact from the parts (protocol v17): a craft stands on its lowest part (the altitude readout is the centre of mass, so a craft on the pad reads a few metres above it), lands on the parts within half a metre of its lowest point and crashes above their lowest crash tolerance, and falls over when its lean plus the terrain slope puts its centre of mass outside the footprint of those parts (`FlightReadout.tipped`; a tipped craft lies on its side and cannot lift off). Per-part breakage on landing and wheels rolling are not simulated.
- Fuel lines: the importer sets `fuel_line_target` for `fuelline*` parts from `Data_CompoundPart.OtherEndAnchor` (struts carry the same module and are left alone); the staging delta-v and the flight resource net both let the fed part draw from the tank the line hangs on, one way. No stock craft has fuel lines.
- EVA ladders (protocol v45): `EvaControls { grab, climb }`: F takes hold of the nearest ladder within 1.5 m (ladder parts, and crewed parts' built-in ladders along their axis: the hatch side is not in the data) or lets go; W/S climbs at the original's `ClimbMoveSpeed` 0.8 m/s, hanging 0.4 m off the ladder and moving with the vessel; Space lets go. `FlightReadout.on_ladder` gives (vessel, part). Boarding counts from the nearest crewed part (within 6 m) and takes the seat at once, then the Kerbal stays a second climbing in (`FlightReadout.boarding`) before the vessel goes.
- Engine gimbals (protocol v44): `FlightReadout.gimbals` gives each gimballing engine of the running stage its turn now (part, about its own X, about its own Z, rad), up to its `gimbalRange`, from the steering command the way control surfaces deflect.
- Crew and resource transfer (protocol v43): `MoveCrew { vessel, kerbal, to_part }` (refused for a part that is full or carries no crew); `TransferResource { vessel, resource, from, to }` fills the receiving tanks with what the giving ones hold, as the original's Resource Manager plans it, over about 10 s (our own rate), draining in proportion to what each tank holds and filling in proportion to its room, then stops (empty lists stop it early). `FlightReadout.part_resources` lists each attached tank (part, resource, stored, capacity) and `transfer` the one running.
- Paint (protocol v42): `Craft.colors` and `CraftPart.colors` (`Option<(base, accent)>`, sRGB bytes; `None` is the agency's colours on a craft and the craft's on a part). The importer reads each part's `Data_Color` from the original's assemblies: the craft takes the pair most parts wear and parts keep theirs only where it differs. Saves, launches, docking (the docked craft's parts keep its paint), debris and `GetVesselCraft` carry them.
- Wrecks: a crash that breaks the root carries the blow on through the parts in line (each crushed layer taking twice its crash tolerance off the speed), and what is left falls apart into its connected pieces as debris (own crafts, through the staging debris path) thrown off with a weak bounce of the impact velocity, some fixed pseudo-random scatter and a tumble; they come to rest on the ground. The vessel itself is Crashed with no parts left.
- Debris crafts: what comes off a vessel (staging or breaking) spawns one debris vessel per connected piece (each radial booster its own), each with the parts it took as its craft (re-rooted, poses and guids kept; `GetVesselCraft` answers for it), the parent's attitude (`facing`, `roll_ref`), a push off to the side for radial pieces and a slow tumble.
- In-flight editing (protocol v41): `MoveToStage { vessel, part, stage }` moves a part between stages that have not fired (the vessel is refitted from its current craft, keeping its stage, crew, tanks, heat, chutes, gear and panels); `ControlFrom { vessel, part }` turns the craft so that part's axis is +Y (SAS, navball and `facing` follow it; the vessel itself does not move; refused landed and for planes), shown as `FlightReadout.control_part`; `RenameVessel`; `DeployAntennas` extends or retracts dishes and whips (`FlightReadout.antennas`; as in the original, a deployable antenna adds to the vessel's CommNet range only while extended). `VesselState.craft_rev` now counts craft changes. `Craft.loose` carries the editor's loose assemblies: saved and loaded with the craft, dropped at launch.
- Players online (protocol v40): `CampaignMember.online` (in the campaign now) and `flying` (the vessel they last commanded, while it exists); `CampaignState` is pushed to everyone else in the campaign when someone joins or leaves.
- Trim, aero overlay, other vessels' crafts (protocol v39): `SetTrim { vessel, pitch, yaw, roll }` (held) adds to the rotation input with SAS off and to the control surfaces' deflection always. `AeroOverlay { vessel, on }` makes that vessel's readout carry `aero_forces` (part, lift kN, drag kN, inertial) from the last step. `GetVesselCraft { vessel }` answers `VesselCraft { vessel, craft }` for any vessel as it stands now; `VesselState.craft_rev` (the count of parts still on) tells the client when to ask again.
- Lesson rockets: the importer turns the vessels in the original's tutorial saves (`tutorials/Tutorial*_Save.json`, the same assembly schema as the stock crafts) into stock crafts named "Lesson 1.1 rocket" and so on, after the stock crafts so their ids stay. Saves without a vessel (1.2, 1.4, 1.7, 2.1-2.3) add none; 1.3's file does not parse.
- Flight staging stack (protocol v38): `FlightReadout.stage_list` is the editor's staging readout computed from the vessel as it is now (its parts and what its tanks hold), with `thrust_now_kn`, `twr_now` and `delta_v_now_mps` at its current air pressure and gravity; `FlightReadout.delta_v_now_mps` totals it.
- Control surfaces move (protocol v37): `FlightReadout.control_surfaces` lists (part, deflection rad) from the steering asked for this step (SAS or the pilot's input as a share of full turning about each axis, `Powered.steer_cmd`): each surface turns so its lift's torque helps, up to its range.
- Slopes and suspension: a vessel on wheels feels gravity along the ground (the height map's rise ahead and behind it), so a rover rolls downhill unless its brakes hold; legs and wheels out take part of a hard landing on their suspension (decelerating at 30 m/s² over their `suspensionDistance`, our own figure) before the parts' crash tolerance counts.
- Control surfaces: elevators, ailerons, rudders and steerable stabilizers (`Data_ControlSurface` range and moving share) add steering torque to SAS and the pilot's input in proportion to the airflow: each moving surface's extra lift at full deflection (dynamic pressure × 0.036 × coefficient × share × lift curve at the range) at its distance from the centre of mass (`Powered.surface_torque_knm`). The surfaces' deflection itself is not sent yet. Test: the stock jet's control authority grows with airspeed.
- Aerodynamic torque: each part's drag and each lifting surface's force act at the part, and their torque about the centre of mass turns the craft every step (`Powered.aero_torque_knm`), so SAS (or the pilot) has to hold against it and a craft with its drag ahead of its centre of mass wants to swap ends; fins behind restore it. Test: the Jumping Flea's fins add restoring torque at 10° off its axis.
- Targets (protocol v36): `SetTarget { vessel, target }` targets another vessel or a body (`TargetId::Vessel` / `Body`); `VesselState.target` gives the distance (to a body's surface), the target's velocity relative to the vessel and the closing speed. `AttitudeMode::Target` / `AntiTarget` hold toward or away from it (refused without a target). Targets are not saved.
- Fairings and cargo bays (protocol v35): a fairing base (`Data_Fairing`, stage type Fairing) shields everything stacked on its top node until it jettisons (its stage, or `DeployFairings`); a closed cargo bay (`Data_CargoBay`) shields the parts whose centres lie inside its box (`SetCargoBays`). Shielded parts take no drag and no re-entry heat; a fairing still on adds its shell's drag (a cone over its payload: Cd 0.3 end on, 0.6 side on, our own figures). Our crafts do not carry the procedural shell's shape, so the payload is the top-node subtree. `FlightReadout.fairings`, `cargo_bays`, `shielded`.
- Resource manager (protocol v34): `FlightReadout.resources` and `stage_resources` list (resource, amount, capacity) in units over the whole vessel and over the tanks the burning stage's engines draw from.
- EVA movement (protocol v33): a Kerbal walks at the original's 0.8 m/s (`WalkMoveSpeed`) and runs at 2.2 m/s (`RunMoveSpeed`) with `EvaControls { run }`; `EvaControls { jump }` hops it off the ground at 2.5 m/s up (our own figure), carrying its run forward ×1.2, with the pack quiet in the air. `Translate` moves it on its jetpack (always on for a Kerbal: 0.25 kN along its axes, burning the pack's propellant), which cannot lift it off Kerbin but can on small moons.
- Astronauts (protocol v32): the importer reads the original's 85 Kerbals (`kerbal_variety_text`: name, veteran, bravery/stupidity/optimism/constitution, looks) into `assets/own/kerbals.json`, veterans first. A campaign hires the first eight (`Campaign.roster`, with when each joined) and hires more as launches need them. `KerbalRoster` answers `KerbalRoster { kerbals }` (status Available, Assigned { vessel }, Eva { vessel }, or Missing for a crashed vessel's crew), and the server pushes it whenever it changes. `LaunchAt` / `LaunchSavedAt` take `crew: Option<Vec<String>>` per seat (refused for Kerbals not on the roster or already flying); without it the seats fill in roster order. KSP2 has no traits or experience, so there are none.
- SAS off (protocol v31): `AttitudeMode::Free` holds nothing; `SetRotation { vessel, pitch, yaw, roll }` (held) accelerates the spin about the craft's axes at the turning torque over the moment of inertia (reaction wheels, gimbals at the thrust used, RCS with its group on), and nothing damps it, so the craft keeps turning until countered or SAS takes over again. `FlightReadout.angvel`. On the runway a plane with SAS off lifts its nose with pitch input (toward its -Z, its top).
- Planes and launch sites (protocol v30): a craft built nose-forward (its root part pointing along the floor, as the hangar builds planes) is turned at launch so it points along craft +Y like a rocket (`structure::level_layout`; its old top becomes -Z) and flies along its nose. It lies level on the ground (`Powered.level`): on its wheels, nose along its compass heading, belly (+Z, sent as `roll_ref`) down; its engines push it along the runway, and above 20 m/s it rotates its nose toward the commanded pitch (at most 12°) so the wings lift it off. It touches down rolling (only the sink rate counts against the parts' crash tolerance) and keeps its wings level in flight (the roll reference is down across the axis). `ServerMessage::LaunchSites` (after `DifficultyOptions`) lists LaunchPad_1..4 and Runway_1: the KSC scene's spawn points placed as the client draws the campus (`flight3d::ksc_pose`: pad 1's spawn on its site, turned -4.66° so the pads line up, rigid). The campus is a built site on Kerbin (`ose_sim::campus`): over the pads, the runways and the campus footprint craft stand on the scene's flat surfaces (each a plane of the scene, so the flat campus rises off the sphere away from pad 1, as drawn) instead of the terrain, which the client sinks under the campus. Planes face down the runway (heading 94.66°); `LaunchAt { craft, site }` and `LaunchSavedAt { id, site }` launch there. Test: the stock jet lies level on its gear, rolls, rotates and lifts off at about 62 m/s. Not modelled: control surface deflection, ground steering by rudder, brakes on landing beyond the wheel brakes.
- Lift (protocol v29, `Module_LiftingSurface`): wings, fins, stabilizers and control surfaces push along their lift axis against the airflow through them: dynamic pressure (Pa) × 0.036 × `deflectionLiftCoeff` × the lift curve of |sin AoA| × its Mach curve, plus their own drag (× 0.015 with the drag curves), using the original's `Default` curve set unless a part brings its own. The force joins the flight model every step (and counts for lifting off the ground). `FlightReadout.lift_kn`; `StageReport.col_m` (centre of lift). Procedural wing sizes are not in our craft data, so every wing piece has its default coefficient. Control surfaces do not deflect yet (turning stays with SAS torque), and lift makes no torque.
- Jets (protocol v29): engines whose propellant includes intake air (`MethaneAir`: Wheesley, Panther, Goliath, Whiplash, Whittle, RAPIER air mode) burn only its fuel ingredients (the importer adds the mixture as a recipe without air) at their Isp, with thrust × the engine's `velCurve` at the Mach number × its `atmCurve` at the air density, and none without oxygen or without an intake on the vessel. `FlightReadout.jet`. Intake air flow itself is not counted.
- RCS (protocol v27, `Data_RCS`): with the RCS action group on, `Translate { vessel, x, y, z }` (craft axes: right, fore along the nose, top; held) pushes the vessel with the thrusters' total `maxThrust` scaled by Isp at the ambient pressure, and the thrusters add torque (each at its distance from the centre of mass) to turning. Propellant (monopropellant, or methalox for the linear methalox thrusters) is drawn through the flow graph at that thrust's mass flow; without it they stop. `FlightReadout.rcs_thrust_kn`, `rcs_firing`. Test: the K2 gains radial speed and burns monopropellant with RCS on, none with it off. Not modelled: per-nozzle directions (every thruster pushes along any axis), turning use of propellant.
- Editor stage report (protocol v26): `StageReport { craft }` answers `StageReport { stages, delta_v_vacuum_mps, com_m, cot_m, thrust_dir }` without saving or launching (v28: wet centre of mass, and the first stage's centre and direction of thrust, craft frame); every `StageReadout` (also in `CraftLaunched`) carries `thrust_asl_kn` (each engine's thrust times its sea-level over vacuum Isp) and `twr_asl` (at the stage's start mass on Kerbin's surface).
- Decoupler push: a stage that fires decouplers pushes the two sides apart with half each decoupler's `ejectionForce` over one 50 Hz step (`Module_Decouple`; 0.5 kN·s for a 1.25 m decoupler, a fifth when the dropped side is under 0.5 t, `GLOBAL_EJECTION_FORCE_SCALE`); the vessel gains it forward, the debris backward. KSP2 has no robotic parts (hinges, rotors) and no EVA construction, so neither is planned.
- Flight controls (protocol v25): `AttitudeMode::Maneuver` holds toward the scheduled burn (its direction from the orbit at the burn time, kept current every step; refused without a burn). `SetRoll { vessel, input }` rolls about the vessel axis at 0.5 rad/s times input and reaction-wheel power; the roll shows in `roll_ref` (rotated from the horizon reference). `ActionGroup { vessel, group, on }` sets or toggles Lights, Rcs, Abort (cuts the throttle and arms the parachutes) and Custom(1..10); crafts carry no action bindings yet, so lights, RCS and the custom groups are switches only (RCS adds no thrust). `FlightReadout.lights/rcs/abort/custom_groups`. Target and anti-target holds wait for targets.
- Quicksave and revert (protocol v25): `QuickSave` stores the live campaign (universe, vessels, progress) in the campaign itself (`Campaign.quicksave`, written with the save file); `QuickLoad` puts it back (`AllowQuickLoad`). Each pad launch remembers the moments before and after it: `RevertToLaunch` goes back to the craft on the pad, `RevertToEditor` to before the launch and hands back the craft (`AllowRevert`). All answer `SaveAck`, and are refused while another player is playing the campaign; a reload keeps the campaign's id, members and quicksave. Revert points are in memory and end with a quickload, a campaign switch or a server restart.
- Resource converters (protocol v24, `Data_ResourceConverter` with its selected formula): fuel cells (Methane + Oxidizer to charge) and the fission reactor (Uranium to charge) run while switched on with `SetConverters { vessel, on }` (they start off, as authored), each input and output at its rate times the authored `conversionRate`, all or nothing in one flow request, so a converter idles when its outputs are full or an input is out. They run on rails too. RTGs were already generators. `FlightReadout.converters` lists (part, on, share running). Test: a fuel cell on the starter rocket's tank refills flat batteries in the dark and stops burning methane once they are full. Not modelled: converter heat and auto shutdown.
- Driving (protocol v23): `Drive { vessel, throttle, steer, brakes }` drives a vessel standing on wheels. The wheels are its folded-out wheel parts (`Data_WheelBase`, legs excluded); motors push with the original's torque curve over the wheel radius (`Data_WheelMotor`, nothing past its last key, so each wheel has its top speed), limited by grip (the vessel's weight), and draw their charge rate at full drive; brakes (`Data_WheelBrakes`) and 2% rolling resistance slow it; steering wheels turn it at speed × tan(0.5 rad × steer) / wheelbase. It drives along the root part's pointing direction laid flat (a rover's probe core along craft +Z). A standing craft keeps a compass heading, sent as its `roll_ref` (craft +Z), so a turned rover shows turned. `FlightReadout.drive_speed_mps` and `brakes`. Test: the Inquisitive Rover drives north at 5-12 m/s on Kerbin, turns right with the steering and brakes to a stop. Not modelled: slopes pushing it, sliding, wheel damage, suspension.
- Campaigns (protocol v22): a server keeps several campaigns. One is live (its universe runs); the others wait on a shelf inside the save file (`SaveFile.shelf`, each a full save). `ListSessions` lists them all (live first, then by last played); `CreateSession` always starts a new campaign (its clock on the first morning at the KSC, the sun 15 degrees up) and joins it; `SelectSession { id }` resumes one; `LeaveSession` leaves for the menu and keeps the campaign listed. Switching is refused while another player is playing the live campaign. The live campaign always goes on the shelf when another is started or resumed, even one nobody has joined, so the server's first campaign stays listed. Saved crafts stay with the player across campaigns. The difficulty options go to every player at Hello (they went only to players without a vessel). Editor crafts that list a mixture tank by its mixture (Methalox) get the ingredients stored, so a VAB-built rocket has fuel.
- Landing gear and hard landings (protocol v21): landing legs and retractable wheels fold out and in with `DeployGear { vessel, deploy }` (legs start folded, wheels and gear out, as authored); folded out they use their `EXTENDED` shape, so legs reach below the engine bell and widen the stance (harder to tip over). A craft stands on its lowest part's box (each part's authored bounds, rotated into the vessel). On a touchdown faster than the parts that touch first can take (`crashTolerance`, within 15 cm of the lowest point), those parts break and take up speed² less tolerance²; the next parts down meet what is left, and anything they alone held breaks off as debris. The vessel is lost only when the break reaches the root. `FlightReadout.gear` lists (part, out). Not modelled yet: suspension travel and wheels rolling.
- Re-entry heating (protocol v20, `ose_sim::thermal`, the original's `ThermalComponentJob` with its `PhysicsSettings` defaults): above Mach 1 the parts the airflow reaches (front to back, each shadowed by the outline of the parts ahead) take 500 · Mach³ · area facing the flow · density^0.53 · Cd^0.3 kW; every part loses heat into the air (50 · 0.026 · wetted area per K, five times faster than it heats, fading out at the top of the atmosphere) and with no flux drifts to the air temperature. Thermal mass is 500 per tonne of dry mass times `thermalMassModifier`. Heat shields above their ablation temperature (1000 K) turn the heat away while facing the flow and burn ablator; a part above its maximum temperature burns up (whatever only it held breaks off; if the root burns the vessel is lost). `HeatEnabled`, `HeatScaling` and `HeatPartDestruction` come from the campaign's difficulty. `FlightReadout.heat` lists (part, K, max K, kW) for parts heating up or above 40% of their limit. Tests: a bare Mk1 pod burns up on a steep return from 45 km at 3.2 km/s; with a 1.25 m shield it comes through cool. Not modelled: engine and exhaust heat (every stock engine's heat curve is zero), conduction between parts, sunlight, coolers.
- Parachutes (protocol v19, `Data_Parachute`): a parachute arms when its stage fires (or with `DeployParachutes`), opens partly once the air reaches its minimum pressure (0.04 atm), fully below its deploy altitude above the ground (1 km; drogues 2.5 km), opening at its animation rates, and drags with the original's semi-deployed and deployed drag cubes; it is torn off if fully opened above about Mach 1 and cut away after landing. `FlightReadout.parachutes` lists (part, state, how open). The starter rocket flies, stages and lands under its chute in a test.
- Walking: a Kerbal on EVA standing on the ground walks at up to 2.5 m/s with the throttle and a level attitude (a steep one fires the jetpack).
- Fuel lines: `CraftPart::fuel_line_target` marks a fuel line hanging on its parent tank and feeding another part. The flow graph gets a one-way edge from the fed part back to the tank, and stack-priority searches drain the far end of a fuel-line chain first, as the original's stack distance does (asparagus boosters empty before the core). The importer converts the original's `fuelline*` compound parts (`Data_CompoundPart.OtherEndAnchor`); no stock craft uses them.
- Solar panels that fold out (`Data_Deployable.extendable`) start folded and make nothing until `DeployPanels` (protocol v16; `panels_deployed` in the readout). Electric charge also runs for vessels on rails (panels, generators and cores through time warp).
- Launch: a craft on the pad starts unlit, as in the original: the throttle does nothing until the first stage press lights the first stage (that press drops nothing). Tanks defined for a mixture (Methalox) are filled with its ingredients, as the original's craft files store them; VAB crafts sent without resources had empty tanks before.
- Missions (`docs/reference-notes/missions.md`): the original's 57 missions with their condition trees, 40 playable with the supported checks (SOI, altitudes, apsides, orbit speed, mass, crew, wheels, parts and part families, activated parts, stored and scored reports, research location, predicted encounters, landings, crashes). Missions are taken on at Mission Control with `AcceptMission` (the first one starts accepted) and only progress once accepted; the server advances accepted missions once a second against the agency's vessels, and a completed mission pays its science when handed in with `TurnInMission` (protocol v18; `MissionInfo.accepted`, `turned_in`, answers `MissionAck`). The first mission completes in a test flight of the K1 to 10 km and back.
- Protocol v9: `FlightReadout.facing` (where the vessel points, unit vector in the body's inertial frame) and `FlightReadout.roll_ref` (the craft's forward side; local north across the axis since roll is not simulated); `ServerMessage::BodyRotation { bodies: Vec<BodySpin> }` right after `BodyCatalog` with each body's `rotation_period_s` and `initial_rotation_deg`.
- `--assets-dir DIR` serves converted game assets (glTF, textures) at `/assets/` with a one-day cache and no index fallback; the service unit points it at `/var/lib/ose/assets` on the container and `install.sh` creates the directory and refreshes the unit when it changes.
- `GET /parts.json` and `GET /resources.json`: the embedded part catalog as `PartInfo` (id, title key, category, size, mass, crew, stage type, `size_m`/`center_m` from the first drag cube or the attach-node bounding box, attach nodes, attach rules, resource containers with capacity and initial units, engines with thrust and vacuum/sea-level Isp, engine/decoupler flags) for thumbnails and the editor, cached one hour; no protocol bump. `SaveCraft` and `LaunchCraft` fill parts that list no resources with their definition containers at `initial_units` (full tanks), so an editor may send empty resource lists. `ose-importer --own-out assets/own` regenerates every committed server asset (bodies, slim parts with bounds, resources, stock craft) in one run.
- Guest sweep: players who never joined the campaign and have been away for `--guest-ttl-s` (default one day) are removed with their vessels and saved crafts every `--guest-sweep-s` (60 s); connected players and campaign members are never swept. Keeps the live server tidy after e2e runs. Tested.
- Craft library (protocol v7): `CraftList` lists the 9 stock crafts (converted by the importer into `assets/own/stock-craft.json`, ids 1..9) plus the player's saved crafts (ids from 1000) with parts, stages, dry/wet mass and delta-v; `SaveCraft`, `DeleteCraft`, `GetCraft` (full document) and `LaunchSavedCraft { id, altitude_m }`. Saved crafts persist in the save file.
- Sessions, difficulty and agency (protocol v6): `ListSessions` -> one shared session (id `shared`, name, mode, UT, last played, players); `SelectSession` joins it; `CreateSession { name, mode, difficulty }` configures it while nobody has joined; `SetAgency { flag_id, colours }` is echoed in `CampaignMember.agency`. `DifficultyOptions` (11 definitions from the imported `DifficultyOptionDefinitions` plus the Easy/Normal/Hard/RocketScientist presets, `assets/own/difficulty.json`) is sent once after `BodyCatalog`. `CampaignState` now carries id, mode, difficulty and `created`.
- Campaign (protocol v5): `JoinCampaign` adds the player to the one shared campaign (idempotent) and `CampaignInfo` reads it; `CampaignState` returns name, start tick, members with join ticks, membership flag and vessel count. Membership lives in the save file.
- Per-stage delta-v (`ose_data::staging::delta_v_by_stage`): stages fire highest id first, decouplers jettison their subtree, engines keep running until jettisoned, each stage burns until the first propellant its engines can reach over crossfeed runs out; Tsiolkovsky with thrust-weighted Isp per stage. Kerbal K2 reads 1375 + 1744 + 3081 = 6200 m/s vacuum over its three burning stages. `CraftLaunched` carries the readout (protocol v4).
- Craft launch: `ClientMessage::LaunchCraft { craft, altitude_m }` validates the craft against the embedded part catalog (`assets/own/parts-catalog.json`, 400 parts with their stowed drag cube and without raw modules, plus `resources.json`), answers `CraftLaunched` with part count, dry and wet mass and a whole-craft vacuum delta-v estimate, and spawns the craft as an owned vessel in a circular orbit (a launch pad replaces this in Phase 6). Session test launches a pod plus Terrier.
- Universe save: time, warp and every vessel (owner, orbit elements, scheduled burn) are written to `--save ose-save.json` every `--save-interval-s` (30 s) and restored at startup, so a server restart keeps the campaign; `--save none` disables. Tested: restart with the same db and save file keeps the player, their single probe, the advanced time and the scheduled burn.
- Accounts for resume continuity: `Welcome.token` identifies the player; a later `Hello` with that token resumes the same player id and keeps their vessels (no duplicate probe). Stored hashed in a small JSON file (`--db ose-accounts.json`, `:memory:` for tests); JSON instead of SQLite so the static Linux server cross-compiles without a C toolchain. Session test covers resume.
- Warp arbitration: each player's `RequestWarp` is a request; the universe runs at the lowest request among connected players, and `TimeState.warp_limited_by` names the player holding it down. Leaving releases the hold. Tested with two clients.
- Burns on rails: `ClientMessage::ScheduleBurn { vessel, ut, prograde, normal, radial }` schedules an impulsive burn in the vessel's orbital frame (`ClearBurn` removes it; `BurnState` answers). The step clamps warp so the burn lands exactly on its tick, applies it, and the streamed `Trajectory` shows the pre-burn patch ending in `Maneuver` followed by the post-burn patches. Test: 841.6 m/s prograde from 100 km gives a 12,000 km apoapsis.
- Protocol v3: on join every player gets a probe in a 100 km Kerbin orbit; the server streams `Vessels` (star-space state, reference body, orbit elements, owner) with every snapshot and `Trajectory` (patched-conic patches with end kind) once a second per vessel. The session test checks both.

## How to run

```
cargo test --workspace
cargo run -p ose-server            # http://127.0.0.1:7777/health
cargo run -p ose-importer          # assets/ksp2/data -> assets/ksp2/converted
cargo run -p ose-bot -- --spawn-server   # play the Mun run against a fresh server, print the step table
cd crates/ose-client && trunk serve
.venv/Scripts/python tools/extract_bundles.py
```

Tooling installed locally: rust 1.99 with `wasm32-unknown-unknown`, trunk 0.22, wasm-bindgen-cli, dotnet 9, ilspycmd 11.1, Python venv in `.venv` with UnityPy.

## Deploy

Live at https://ose.jfly.dev/ (home network and Tailscale).
