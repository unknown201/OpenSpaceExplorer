# OpenSpaceExplorer: architecture and phased plan

Goal: a personal, multiplayer rebuild of Kerbal Space Program 2 with a Rust authoritative server and a Rust/WASM browser client. The original install (see `01-ksp2-install-survey.md`) is the reference implementation and the placeholder asset source until we generate our own.

## Guiding decisions

1. **One simulation crate, two hosts.** All game rules live in `ose-sim`, a deterministic, allocation-light Rust crate with no I/O. The server runs it natively; the client compiles the same crate to WASM for prediction and for single-player. One codebase, one source of truth, no drift between "server rules" and "client rules".
2. **Server authoritative.** The server owns time, vessel state, resources, staging and the save. Clients send intents (throttle, attitude, stage, build, warp request) and receive snapshots plus deltas. This is what makes multiplayer tractable.
3. **Integer time, analytic orbits.** Universal time is an integer tick count (for example 1/50 s). On-rails vessels are Keplerian elements evaluated analytically at any tick, so warp is free. Only vessels inside a physics bubble get integrated rigid-body dynamics.
4. **Shared time warp, lowest wins.** Everyone is in the same universe at the same UT. Warp is a request; the server grants the minimum of all players' acceptable warp (a player in atmosphere or under thrust caps it at physics warp). This is simpler and more co-op than per-player subspaces and avoids the time-travel paradoxes of the KSP1 multiplayer mods. Subspaces can be revisited later.
5. **Data from JSON, geometry from bundles, both regenerated by scripts.** Parts, bodies, resources and missions are imported from the KSP2 JSON into our own schema. Meshes and textures are converted to glTF/KTX2 as placeholders. Nothing extracted is committed.
6. **Reference, not copy.** Decompiled C# is read to understand algorithms (patched conics, resource flow, delta-v, staging) and then re-implemented in Rust with our own tests. No decompiled code is committed or transliterated line by line.
7. **Web-first rendering.** `wgpu` targeting WebGPU, with a WebGL2 fallback. Scaled-space (map/planet view) and local-space (physics bubble) renderers mirror the original's two-space design, because that design is what makes planetary scale work with f32 GPUs.

## Repository layout (Cargo workspace)

```
crates/
  ose-math        f64 vectors, quaternions, Kepler solvers, reference frames
  ose-data        Our schemas: Part, PartModule, Resource, CelestialBody, Craft, Mission (serde, versioned)
  ose-sim         Universe: bodies, vessels, part graph, resource flow, staging, patched conics, physics bubble
                  (rapier3d for rigid bodies and joints, feature-gated so headless tests stay fast)
  ose-net         Protocol: messages, snapshot/delta encoding, interest management
  ose-server      tokio + axum: WebSocket sessions, lobby, save/load, warp arbitration, serves the client
  ose-client      WASM: wgpu renderer, egui UI, input, prediction, asset streaming (wasm-bindgen + trunk)
  ose-importer    Reads the Steam install: Addressables catalog, bundle extraction, JSON -> ose-data,
                  meshes -> glTF, textures -> KTX2, Wwise -> ogg (drives UnityPy/AssetRipper where needed)
tools/            Python helpers (UnityPy scripts), dev scripts, CI
assets/own/       our generated assets (committed)
assets/ksp2/      extracted placeholders (gitignored, rebuilt by ose-importer)
reference/        ilspy decompile output (gitignored)
docs/             these documents, ADRs, STATUS.md
```

Technology choices:

| Area | Choice | Reason |
|---|---|---|
| Server runtime | tokio, axum | WebSocket and HTTP in one binary; also hosts the static client |
| Transport | WebSocket first, WebTransport later | WebSocket works everywhere today; WebTransport adds unreliable datagrams for deltas later |
| Serialization | postcard for the wire, serde JSON for data files and saves | Small packets, human-readable data |
| Physics | rapier3d (f32, local bubble, origin rebased) | Pure Rust, compiles to WASM, deterministic with its determinism feature |
| Orbits | own Kepler and patched conics in f64 | Must match KSP behaviour; no crate does SOI transitions |
| Rendering | wgpu | Native and WebGPU from one code path, WebGL2 backend as fallback |
| UI | egui at first | Fast to iterate, runs in WASM; a DOM overlay can replace it if the HUD needs rich text |
| Client build | trunk + wasm-bindgen | Standard Rust web toolchain |
| ECS | hecs inside ose-sim | Keeps the sim independent of any engine |

## Multiplayer model

- A **session** is one universe (one save). The server loads it, ticks it, autosaves it.
- Each player has a **focus**: a vessel, a building, or the map. The server sends full fidelity for the player's physics bubble and a coarse feed (orbital elements only) for everything else.
- **Physics bubbles**: any vessel within a few km of a focused vessel is simulated with rigid bodies on the server. Everything else is on rails. Two players near each other share one bubble.
- **Client prediction** runs ose-sim locally for the player's own vessel between snapshots and reconciles on each snapshot. Other players' vessels are interpolated.
- **Warp arbitration**: server-granted, lowest wins, with a HUD showing who is holding warp down.
- **Building**: the editor is client-side; a finished craft is uploaded as a Craft document and spawned by the server at a launch site. Shared editing is out of scope.
- **Persistence**: one JSON save per session, versioned by the ose-data schema version, plus periodic snapshots.

## Phased plan

Each phase ends with something runnable and a `docs/STATUS.md` update. Phases 1 to 3 are sequential; later ones can overlap.

**Phase 0: Scaffolding.** Cargo workspace, crate stubs, CI (fmt, clippy, test, wasm build), gitignore for `reference/` and `assets/ksp2/`, ADR template. Done when `cargo test` and `trunk build` pass on empty crates.

**Phase 1: Importer and data model.** ose-importer parses `catalog.json`, finds bundles by key, extracts TextAssets with UnityPy, and converts the ~200 part JSONs, the celestial body JSONs and the resource definitions into ose-data. Decompile Assembly-CSharp into `reference/` for study. Done when ose-data round-trips every part and body under a schema test, and a report lists every field not mapped.

**Phase 2: Orbital core.** ose-math and the on-rails half of ose-sim: body hierarchy from imported data, Kepler propagation, SOI transitions, patched-conic prediction, maneuver nodes, time warp. A headless CLI loads the Kerbol system and propagates a vessel. Done when a Kerbin to Mun transfer matches the original game's numbers within tolerance.

**Phase 3: Map view client.** ose-client renders scaled space: bodies as spheres with placeholder textures from the scaled bundles, orbit lines, time and warp HUD, camera. Single-player, local sim. Done when the Kerbol system runs in a browser.

**Phase 4: Server and first multiplayer.** ose-server hosts a session, two browser tabs join, both see the same UT and vessels, warp arbitration works. Snapshot/delta protocol and prediction land here. Done when two players each place a probe in orbit and see each other's.

**Phase 5: Vessels, parts and assembly.** Part meshes as glTF placeholders, the part graph with attach nodes, the editor (symmetry, staging), resource containers and flow, engines with Isp curves, staging and decouplers. Done when a stock craft JSON from the install loads in the editor and launches on rails with the correct delta-v.

**Phase 6: Local physics.** rapier bubble: rigid bodies, part joints, thrust, drag, gravity, surface collision against heightmap terrain, origin rebasing. Done when a rocket lifts off from KSC to orbit under player control while a second player watches live.

**Phase 7: Planets and terrain.** Quadtree terrain with heights from the simulation bundles (or our own noise), atmospheres, scatter. Landing on the Mun.

**Phase 8: Content and polish.** Science, tech tree, missions from the mission JSON, kerbals, audio (Wwise conversions), effects.

**Phase 9: Own assets.** Replace placeholders with generated parts, textures and planets (reusing the LostInTime generation pipeline), so the game no longer depends on the Steam install at runtime.

## Open questions

1. Co-op scope: one shared campaign save progressed together (recommended), or separate agencies in one universe?
2. Hosting: LAN and self-hosted only (recommended, no accounts), or internet-reachable with logins?
3. Browser support: WebGPU-only early builds (Chrome/Edge), or WebGL2 from day one?
4. Reference depth: decompile all of Assembly-CSharp locally for study (recommended, personal use), or work only from the JSON data and public knowledge of KSP mechanics?
